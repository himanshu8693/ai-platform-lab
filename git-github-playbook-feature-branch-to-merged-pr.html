1 — Key concepts & branch model

BranchWhat it isWhen to target
mainNext unreleased version. All new features and fixes go here first.Always — this is the primary PR target
release/2.0.xActive long-lived maintenance branch for the 2.0 series. Patch releases (2.0.1, 2.0.2 …) are cut from here.Backport after merging to main
release/1.22.xActive maintenance branch for 1.22 seriesBackport after merging to main
release/1.21.xActive maintenance branch for 1.21 series (customer version)Backport after merging to main
release/2.0.0Frozen snapshot of the 2.0.0 GA tag — do not targetNever target directly
Rule: Always raise your PR against main first. After merge, backport to the relevant release/x.y.z branches using cherry-pick or the automated backport bot.

2 — One-time setup

Configure git identity
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
Authenticate GitHub CLI (gh)
gh auth login          # follow prompts — choose SSH or HTTPS
gh auth status         # verify you are logged in
Clone the repo (first time only)
git clone git@github.com:hashicorp/consul-enterprise.git
cd consul-enterprise

3 — Create a feature branch

Always branch off the latest main so your work is as close to the merge target as possible.

Fetch latest state from remote and branch off main
git fetch origin                        # download all remote updates
git checkout -b feature/my-fix origin/main
# Convention: feature/<short-description>  or  fix/<short-description>

Example from PR #13027:

git checkout -b feature/api-gw-suppress-envoy-headers origin/main
Naming tip: Use feature/ for new capabilities, fix/ for bug fixes, backport/ for cherry-picks to release branches. Keep it lowercase with hyphens.

4 — Make & commit code changes

Stage and commit

# Stage specific files (preferred — never use "git add .")
git add agent/xds/config/config.go
git add agent/xds/listeners.go
git add agent/xds/listeners_apigateway.go

# Commit with a meaningful message
git commit -m "agent/xds: add envoy_suppress_envoy_headers config key for API Gateway

Add a new ProxyConfig key that sets ServerHeaderTransformation=PASS_THROUGH
on the HttpConnectionManager for API Gateway HTTP listeners.

Usage:
  spec:
    config:
      envoy_suppress_envoy_headers: true"
Never commit: binary files, built binaries, *.log files, or secrets. Check git status before staging.

Check what you have staged / unstaged

git status                   # summary of changed files
git diff                     # unstaged changes (line-by-line)
git diff --staged            # staged changes (what will be committed)
git diff --stat              # summary: files changed, insertions, deletions

Undo a mistake before pushing

git reset HEAD <file>        # unstage a file
git checkout -- <file>       # discard changes in a file (cannot be undone)
git reset --soft HEAD~1      # undo last commit, keep changes staged

5 — Add a changelog entry

This repo requires a changelog file named after the PR number. The PR number is only known after you open the PR — so either add it after opening, or use a placeholder and amend.

File: .changelog/<PR_NUMBER>.txt
# Format — pick the correct type:
#   release-note:improvement   new feature or enhancement
#   release-note:bug           bug fix
#   release-note:deprecation   deprecating something
#   release-note:note          general note

```release-note:improvement
xds: **(Enterprise only)** Add two new opt-in `ProxyDefaults.spec.config` keys
for controlling the `server` response header on API Gateway HTTP listeners:
`envoy_suppress_envoy_headers` (removes the header entirely) and
`envoy_server_header_name` (renames it to a custom value).
```
Stage and commit the changelog file
git add .changelog/13027.txt
git commit -m "changelog: add entry for PR #13027"

6 — Push the branch

# First push (sets upstream tracking)
git push -u origin feature/api-gw-suppress-envoy-headers

# Subsequent pushes (normal)
git push

# Force-push after a rebase (use --force-with-lease, NOT --force)
git push origin feature/api-gw-suppress-envoy-headers --force-with-lease
# --force-with-lease is safer: it refuses if someone else pushed to the same branch

Using GitHub CLI (gh)

gh pr create \
  --base main \
  --head feature/api-gw-suppress-envoy-headers \
  --title "agent/xds: add envoy_suppress_envoy_headers and envoy_server_header_name" \
  --body "### Description
...
### Testing
...
### PR Checklist
* [x] updated test coverage
* [x] appropriate backport labels added
* [x] not a security concern"

View the PR you just created

gh pr view 13027                         # human-readable summary
gh pr view 13027 --json number,title,baseRefName,state,url

Edit PR title or description later

gh pr edit 13027 --title "new title"
gh pr edit 13027 --body "new full body text"

8 — Add backport labels

Labels tell the backport automation which release branches to cherry-pick to after merge. Always add both the CE and ENT variant for each release line.

List all available backport labels
gh label list --limit 100 | grep backport
Add labels to an open PR
gh pr edit 13027 \
  --add-label "backport/1.21" \
  --add-label "backport/ent/1.21" \
  --add-label "backport/1.22" \
  --add-label "backport/ent/1.22" \
  --add-label "backport/2.0" \
  --add-label "backport/ent/2.0"
Verify labels were applied
gh pr view 13027 --json labels | python3 -c \
  "import json,sys; [print(l['name']) for l in json.load(sys.stdin)['labels']]"
LabelWhat it does
backport/1.21Bot cherry-picks to release/1.21.x (CE code)
backport/ent/1.21Bot cherry-picks to release/1.21.x (ENT-specific code)
backport/1.22Bot cherry-picks to release/1.22.x (CE code)
backport/ent/1.22Bot cherry-picks to release/1.22.x (ENT-specific code)
backport/2.0Bot cherry-picks to release/2.0.x (CE code)
backport/ent/2.0Bot cherry-picks to release/2.0.x (ENT-specific code)

9 — Update an open PR (retarget / rebase)

Retarget PR to a different base branch

# Change PR base from release/2.0.0 → release/2.0.x → main
gh pr edit 13027 --base release/2.0.x
gh pr edit 13027 --base main

Rebase feature branch onto a different base (after retargeting)

# Scenario: branch was on release/2.0.x, now retargeting to main
# cc11b9a6c8 = the last commit on release/2.0.x BEFORE our 2 commits
# --onto transplants ONLY our commits onto main, skipping all intermediate history

git fetch origin
git rebase --onto origin/main cc11b9a6c8 feature/api-gw-suppress-envoy-headers
# If conflicts: fix files, then: git add <file> && git rebase --continue
# To abort: git rebase --abort

git push origin feature/api-gw-suppress-envoy-headers --force-with-lease
How to find cc11b9a6c8 (the fork point):
git merge-base feature/api-gw-suppress-envoy-headers origin/release/2.0.x
This prints the common ancestor commit — use that as the third argument to --onto.

Keep branch up-to-date with main (no rebase needed for simple additions)

git fetch origin
git merge origin/main              # merge latest main into your branch
# OR (cleaner history, but rewrites commits):
git rebase origin/main             # replay your commits on top of latest main

10 — Triage CI failures

Check PR CI status

gh pr checks 13027                            # one-line summary of all checks
gh pr checks 13027 2>&1 | grep -v "pass\|skip" # show only failures/pending

Get detailed failure logs

# Get run ID and job ID from gh pr checks output, then:
gh run view <RUN_ID> --log-failed          # show only failed steps
gh run view --job <JOB_ID> --log           # full log for one job

# Or via API (useful for completed jobs):
curl -sL \
  -H "Authorization: Bearer $(gh auth token)" \
  "https://api.github.com/repos/hashicorp/consul-enterprise/actions/jobs/<JOB_ID>/logs" \
  | grep -i "FAIL\|Error\|panic"

Re-run a failed workflow

gh run rerun <RUN_ID> --failed   # re-run only the failed jobs
gh run rerun <RUN_ID>            # re-run the entire workflow

Force a fresh CI run (e.g. to retrigger CodeQL)

# Push an empty commit — this triggers all PR workflows fresh
git commit --allow-empty -m "ci: trigger re-run"
git push

Common CI failures and what they mean

Check nameCommon causeFix

Verify Branch AncestryBranch not descended from target baseRebase onto correct base and force-push

11 — Merge the PR

Only merge once all required checks are green and the PR is approved.

# Squash merge (all commits squashed into one — preferred for feature branches)
gh pr merge 13027 --squash \
  --subject "agent/xds: add envoy_suppress_envoy_headers and envoy_server_header_name (#13027)" \
  --body "Squash merge of PR #13027. Summary of changes..."

# Verify it merged
gh pr view 13027 --json state,mergedAt,mergeCommit | python3 -c \
  "import json,sys; d=json.load(sys.stdin); print(d['state'], d['mergedAt'], d['mergeCommit']['oid'])"
Merge strategies:
--squash — collapses all commits into one clean commit on the base branch. Best for feature branches with many WIP commits.
--merge — creates a merge commit. Preserves all individual commits.
--rebase — replays commits individually on the base branch.

12 — Backport to release branches

After merging to main, the fix needs to reach the active maintenance branches. The backport bot may do this automatically based on labels — but always verify and fill in any gaps manually.

Step 1 — Find the merge commit SHA

git fetch origin
git log origin/main --oneline | grep "13027\|your-feature-description" | head -3
# Example output: 874c087476 agent/xds: add envoy_suppress_envoy_headers (#13027)

Step 2 — Check if the bot raised PRs automatically

gh pr list --search "backport-13027 OR 13027 in:title" --limit 20 \
  --json number,title,baseRefName,state \
  | python3 -c "import json,sys; [print(r['number'],r['state'],r['baseRefName'],r['title'][:60]) for r in json.load(sys.stdin)]"

Step 3 — Close duplicate auto PRs if bot created more than one

gh pr close 13114 --comment "Closing duplicate — keeping PR #13113."

Step 4 — Manually cherry-pick for any missing branch

# Create a backport branch off the target release branch
git checkout -b backport/13027/release-1.22.x origin/release/1.22.x

# Cherry-pick the merge commit from main
git cherry-pick 874c087476
# If conflicts arise:
#   1. Open the conflicted file and resolve manually
#   2. git add <resolved-file>
#   3. git cherry-pick --continue
# To abort: git cherry-pick --abort

# Verify the diff looks correct (same 4 files, same +/- numbers)
git diff origin/release/1.22.x...backport/13027/release-1.22.x --stat

# Push
git push origin backport/13027/release-1.22.x

Step 5 — Raise the backport PR

gh pr create \
  --base release/1.22.x \
  --head backport/13027/release-1.22.x \
  --title "Backport of agent/xds: add envoy_suppress_envoy_headers into release/1.22.x" \
  --body "Backport of PR #13027. Cherry-picked from merge commit 874c087476.

Original PR: https://github.com/hashicorp/consul-enterprise/pull/13027" \
  --label "theme/envoy/xds"

Repeat Step 4–5 for each missing release branch

# For release/2.0.x
git checkout -b backport/13027/release-2.0.x origin/release/2.0.x
git cherry-pick 874c087476
git diff origin/release/2.0.x...backport/13027/release-2.0.x --stat
git push origin backport/13027/release-2.0.x
gh pr create --base release/2.0.x --head backport/13027/release-2.0.x \
  --title "Backport of agent/xds: ... into release/2.0.x" \
  --body "Backport of PR #13027 ..." --label "theme/envoy/xds"
Watch out for copyright header conflicts: Different release branches may have different copyright styles (HashiCorp vs IBM Corp.). Git's three-way merge usually handles this automatically — always check git diff --stat after cherry-pick to confirm no unexpected files changed.
